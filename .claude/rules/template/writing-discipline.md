## 執筆の規律

### 説明は1箇所に集約する

同じ概念を2箇所で説明しない。読者は毎回「同じか別か」の照合コストを払う。
**表現を変えて言い直すと照合コストはさらに上がる。**
2箇所目は参照に留める。

「大事だから2回書く」は誤り。大事な概念は1箇所で強く書き、以降は同じ語で参照する。

### 用語予算を守る

新規概念（造語・略語を含む）の総数に上限を設ける。
目安は文書全体で10〜12、うち最後まで覚えている必要があるものは5〜7。

**定義したのに一度も使わない略語は削除する。** 太字と括弧書きの英語綴りは
「重要だから覚えろ」という強い合図であり、回収がないと記憶コストの丸損になる。

### 段落は主張から始める

主張を先頭に置き、以降を根拠にする。主張を受け入れた読者が残りを捨てられる。
手順や列挙から始まる段落は、読者が「覚えるべきか、結論だけでよいか」を判断できない。

### 図表は本文と同じ直列化に載せる

図が本文より先に置かれると、キャプション中の未定義概念がまとめて注入され、
ほぼ確実に最大の負荷スパイクになる。**図はそれが描く概念群の直後に置く。**

キャプションは図の内容の説明で終わらせず、**その図が支持する主張**を書く。

### 主観的な訴えを額面通りに受け取らない

「詳しすぎる」「実装寄りすぎる」「読みにくい」といった訴えの正体は、
たいてい**詳細さそのものではなく配分の偏り**である。
節ごとの分量を実測してから判断する。方法の記述が「独自性」の節に肥大し、
「研究方法」の節が痩せている、といった倒錯がよく起きる。

### 点検と書き換えを分ける

点検結果を出したらいったん止め、反映範囲の指示を待つ。
並べ替えは意味を変えずに実施できるが、欠落した導出の補筆は書き手の意図が要る。

### 調べたことは docs/ に蓄積する

一次資料から採取した事実、参考にした作法、判断の根拠は `docs/` に主題ごとに残す。
セッションが長くなると忘れるし、次のセッションには引き継がれない。
**「調べ直せばいい」は毎回のコストであり、しかも前回と違う結論になりうる。**

### 導入は最後に書く

文書の導入（はじめに・背景・概要・要旨）は、本体が確定してから書く。
**論文に限らず、申請書・提案書・報告書・設計文書のいずれでも成り立つ一般則である。**

- 導入の仕事は**これから来るものを設定すること**。来るものが決まる前に書けば必ず外れる
- 早く書いた導入は**錨になる**。本体が導入に合わせて歪む
- 導入は**最も書き直される部分**。早く書いた労力はほぼ捨てることになる

書き上がった導入が立派だと、それに合わせて本体を歪める誘惑が生じる。
これは結果に合わせてゴールを書き換えるのと同じ失敗である。

### 他分野の作法をそのまま持ち込まない

執筆手法には出自がある。論文向けに最適化された質問リストや章立てを
申請書へそのまま当てはめると、形は整うが評価されない文書ができる。

**借りるのは装置であって、中身ではない。**
質問票という装置は一般に使えるが、質問項目は文書ごとに
一次資料（様式・評価基準）と二次資料から作り直す。

### 同期の仕組みとレビュー機能は競合しうる

外部ツールと同期しながら書く場合（Overleaf の git 連携、Google Docs の API 更新など）、
**同期による上書きが、共著者のコメントやトラックチェンジを消すことがある。**

例: Overleaf 公式は git 連携について
「pushes from Git to Overleaf can result in the loss or displacement of track changes and
comments. Consequently, we do not recommend mixing active use of Git and the use of
track changes and/or comments」と明記している。
さらに **git 側でのファイル改名は、Overleaf 側では delete + create になり、
そのファイルのコメントが消える。**

**共著者と共有する前に、使っている同期方式とレビュー機能の相性を必ず確認する。**
競合する場合の運用は次のいずれか。

1. **レビュー期間中は同期を凍結する。** コメントが出揃ったら取り込み、反映後に再開する
2. レビューを別の媒体で行う（PRレビュー、別ファイル、別プロジェクト）

いずれの場合も、**共有開始後にファイルを改名・移動しない。**
改名が必要なら共有前に済ませること。
