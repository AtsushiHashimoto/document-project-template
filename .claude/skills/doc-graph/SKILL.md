# Doc Graph — マクロ直列化

文書全体を概念の依存グラフとみなし、段落レベルの順序を決める。
**段落の中の文レベルは扱わない。** それは `/doc-paragraph` の仕事。

## 前提

`.doc/constraints.md` と `.doc/criteria.md` が存在すること。
無ければ先に `/doc-init` を実行する。**この2つを読まずにグラフを作ってはいけない。**

## Step 0: 制約の読み込み

`.doc/constraints.md` から**記載項目の順序**を、`.doc/criteria.md` から**評定要素の一覧**を
読む。以降の直列化はこの2つの制約下で行う。

## Step 1: 概念の抽出と分類

本文を通読し、概念を2つに分ける。**数えるのは C だけ。**

- **前提 W** — 読者が既に知っているか、観察事実として提示されるもの
- **導出概念 C** — この文書が新たに定義・主張するもの

判定基準: その語を初出時に定義しているなら C。定義せずに使えているなら W。

## Step 2: 依存グラフの構築

各 C について `W1 ∧ C2 → C3` の形で導出規則を書き下す。あわせて記録する。

- C 間の依存関係
- 各 C の**消費点**（どこで使われるか）。導入から消費までが**生存区間**
- 導出規則が書けない C（＝論理的に浮いている。削除または導出の補筆が要る）

## Step 3: 現在の直列化のトレース

本文の順に読み進め、各地点の **live set**（導入済みかつ未消費、または今必要な C の集合）を数え、
前方参照・負荷スパイク・再説を検出する。行番号を必ず付ける。

**図表を忘れない。** 図が本文より先に置かれていないか、キャプションが未定義概念を
注入していないかを必ず確認する。

## Step 4: 評価基準への対応表

`.doc/criteria.md` の評定要素を縦に並べ、各要素に対応する記述箇所を書く。
**空欄が欠落。** 欠落は認知負荷側の指摘より優先度が高い。

## Step 5: 制約下での再直列化

形式制約の項目順を外枠として固定し、**各項目の内部**を依存グラフのトポロジカル順序で並べる。

- 各 C はその全前提の後に置く（前方参照ゼロ）
- 生存区間が短くなるよう、導入と消費を近づける
- 各 C の説明は1箇所に集約し、他所からは参照のみ
- 図はそれが描く C 群の**直後**に置く
- 各ステップで **discharge される概念**（読者が捨ててよくなるもの）を明記する

形式制約と衝突が残る場合は、前の項目で前提を先出しし後の項目を詳細化に留める。
**その構造を採ったことを `.doc/graph.md` に明記する。**

## Step 6: 書き出し

**会話に書いて終わりにしない。** 結果は必ず `.doc/graph.md` に永続化する。
冒頭に対象ファイル名、**対象のコミットハッシュまたは日付**、点検日、使用した制約の版を記録する。
どの版に対する点検かが分からないノートは無価値になる。

含める内容:

1. W と C の一覧（C には導出規則を併記）
2. 依存グラフ（`W1 ∧ W2 → C1` の連鎖として）
3. live set の推移と、検出した前方参照・スパイク・再説（行番号と対処方針つき）
4. 評定要素 → 記述箇所の対応表と、欠落の一覧
5. 再直列化案（順序と discharge される概念）
6. 未実施であることの明示。**並べ替えだけで済むもの／集約が要るもの／加筆が要るもの**に分類する

会話には要約（違反の件数、最重度のもの、再直列化の差分の要点、欠落の件数）だけを書く。

## Step 7: 停止

**点検と本文の書き換えは別の作業。** ここでいったん止め、どこまで反映するかの指示を待つ。
並べ替えは意味を変えずに実施できるが、欠落した導出の補筆は書き手の意図が要る。

反映を実施する場合は、違反ごとに issue を切る。
「どの制約を満たすための変更だったか」が後から追えるようにするため。
