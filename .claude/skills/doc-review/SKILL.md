# Doc Review — 提出前の総点検

`/doc-constraints` `/doc-coverage` `/doc-graph` `/doc-numbers` `/doc-readability` を順に通し、結果を統合して報告する。

## Step 1: 形式制約の遵守

- 記載項目が指定の順序で並んでいるか
- **削除必須の指示書き・留意事項を外した状態で**分量が上限内か
- 体裁（フォントサイズ、色、見出し位置、空白頁の扱い）
- 共著者・分担者の役割が本文に書かれているか

**1つでも違反があれば、内容の点検より先に報告する。** 形式違反は内容と無関係に落ちる。

## Step 2: 評価基準への対応

`/doc-coverage` を実行し、× と △ の要素を列挙する。
重大度「高」が1件でもあれば、提出前に必ず解消する。

## Step 3: 直列化

`/doc-graph` を実行し、前方参照・負荷スパイク・再説の残存を確認する。

## Step 4: 数値

`/doc-numbers` を実行する（正典は `numbers.md`。モデル指定なし）。
台帳と所見を受け取る。**数値・金額を記入した直後の版では必ず回す。**

## Step 5: 読みやすさ

`/doc-readability` を実行する（基準は `readability.md`。
**モデル指定あり: doc-readability-reviewer エージェント経由で Fable が実行する**）。
提案はdiff形式で受け取り、この段階では適用しない。

## Step 6: 統合報告

次の順で報告する。**この順序は重大度順であり、直す順序でもある。**

1. 形式違反（あれば即座に修正）
2. 独立絶対評価項目の欠落
3. その他の評定要素の欠落／**基準10（擁護の材料）の欠落**
4. **数値の誤り（算術・出典との不一致・文書内の食い違い）**。
   一つの食い違いが文書全体の信頼を毀損するため、内容の巧拙より優先する
5. 前方参照・負荷スパイク
6. 再説（集約すれば分量が浮くので、2〜3の加筆の原資になる）
7. 段落レベルの指摘
8. 読みやすさの摩擦、検証不能な数値、見かけの矛盾の橋渡し提案（適用は指示待ち）

## Step 7: 最終確認

- 提出物のファイル形式・命名は指定どおりか
- 締切までの残り時間
- 提出前に外すべきもの（指示書き、コメント、`[[要確認]]` 等の作業用マーカー）が残っていないか

```sh
grep -rn "要確認\|TODO\|FIXME\|\[\[" <対象ファイル>
```
