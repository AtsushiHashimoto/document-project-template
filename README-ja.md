# Document Project Template

**外形が定まった文書**（研究費申請書、論文、提案書、規格文書、報告書）を、
Claude Code と Issue 駆動で書くためのテンプレート。

[English](README.md)

## 何のためのテンプレートか

外形が定まった文書には、書き手の力量とは独立に落ちる原因が3つある。

1. **形式違反** — 様式が定める項目順・字数・体裁を守っていない
2. **評価基準への非対応** — 評価者のチェックリストに対応する記述が見つからない
3. **論理の直列化の失敗** — 内容は正しいのに、読む順序が悪くて理解されない

このテンプレートは、この3つを**執筆の前に片付ける手順**として固定する。

```
1. 形式を確認する            → .doc/constraints.md
2. 評価基準を確認する         → .doc/criteria.md
3. 論理をグラフ化し、1を守った範囲で
   2が評価可能な形になるよう、
   認知負荷が最小になるよう直列化する → .doc/graph.md
```

**3 は2階層に分ける。** 文書全体の段落レベル（マクロ）と、いま書いている段落の中の
文レベル（ミクロ）は別の作業であり、混ぜると両方が雑になる。

## ワークフロー

```
┌─ 準備（プロジェクト開始時に一度）────────────────────────────┐
│                                                              │
│  /doc-init          形式と評価基準を一次資料から採取           │
│      ↓              最後に「権威ある二次資料はあるか」を質問   │
│  /doc-references    二次資料を読み評価軸の解釈を補強           │
│      ↓                                                       │
│  /doc-questions     この文書専用の質問票を生成                 │
│                     （既製の質問票があればそれを土台に）        │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌─ 設計 ───────────────────────────────────────────────────────┐
│                                                              │
│  /doc-graph         概念の依存グラフ → 段落レベルの順序        │
│      ↓                                                       │
│  /doc-outline       全問のトピックセンテンスだけを書く         │
│                     縦読み検査 → ★ユーザーと対話して確定★     │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌─ 執筆（質問ごとに繰り返す）──────────────────────────────────┐
│                                                              │
│  /doc-paragraph     その段落の中を文レベルで直列化             │
│      ↓                                                       │
│  /doc-answer <N>    1問ずつ対話しながら段落に展開              │
│                                                              │
│  骨格が変わる指摘が出たら /doc-outline か /doc-graph へ戻る    │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌─ 点検 ───────────────────────────────────────────────────────┐
│                                                              │
│  /doc-coverage      評定要素 → 記述箇所の対応表と欠落一覧      │
│      ↓              （欠落の解消は読みやすさの改善より優先）    │
│  /doc-review        形式・評価・直列化の総点検                 │
└──────────────────────────────────────────────────────────────┘
                          ↓
┌─ 提出後 ─────────────────────────────────────────────────────┐
│                                                              │
│  /doc-harvest       質問票を再利用資産として docs/ に残す      │
│                     結果が出たら評点・コメントを追記           │
└──────────────────────────────────────────────────────────────┘
```

### 最短の使い方

```
/doc-init            # 様式と審査基準を渡す。二次資料の有無を聞かれる
/doc-questions       # 質問票ができる
/doc-outline         # トピックセンテンスだけ埋める。ここで一番議論する
/doc-answer 1        # 1問ずつ書く
...
/doc-review          # 提出前
/doc-harvest         # 提出後
```

### やってはいけない順序

| ❌ | なぜ |
|---|---|
| `/doc-init` を飛ばして書き始める | 形式は順序の制約、評価基準は存在の制約。どちらも後付けできない |
| `/doc-outline` を飛ばして本文を書く | 本文まで書くと惜しくなり、誤った骨格のまま辻褄を合わせにいく |
| 冒頭の節から順に書く | 中核が決まらないうちに外側を書くと全部書き直しになる。背景と概要は最後 |
| `/doc-coverage` の前に体裁を整える | 後から欠落が見つかると分量の再配分で推敲がやり直しになる |

## スキル一覧

| スキル | 層 | 用途 |
|--------|-----|------|
| `/doc-init` | 準備 | 形式と評価基準を一次資料から採取。**一文字も書く前に実行** |
| `/doc-references` | 準備 | 権威ある二次資料で評価軸の解釈を補強する |
| `/doc-questions` | 準備 | この文書専用の質問票を生成する |
| `/doc-constraints` | 1 | 形式制約の確認・再採取 |
| `/doc-criteria` | 2 | 評価基準の確認・再採取 |
| `/doc-coverage` | 2 | 評定要素 → 記述箇所の対応表と欠落検出 |
| `/doc-graph` | 3-マクロ | 概念依存グラフ。段落レベルの順序を決める |
| `/doc-outline` | 3-マクロ | トピックセンテンスのみ先行。**3節以上では必須** |
| `/doc-paragraph` | 3-ミクロ | 段落の中を文レベルで直列化。書く直前に毎回 |
| `/doc-answer` | 執筆 | 1問ずつ対話しながら段落に展開 |
| `/doc-review` | 提出前 | 1・2・3 の総点検 |
| `/doc-harvest` | 提出後 | 質問票を再利用資産として残す |

## 質問票について

**文書は質問への回答の集まりである。** 全体を考えると途方に暮れるが、
各質問に分割すれば1問ずつ片づけられる。

この考え方は慶應義塾大学 杉浦孔明研究室の
**「60 Questions & Answers」**（国際会議論文は約60段落からなり、
60個の質問に答えれば論文が完成する）に着想を得ている。
本テンプレートはそれを、**一次資料と二次資料から文書ごとに質問票を自動生成する**
形へ一般化したものである。

質問票は使うたびに良くなる。`/doc-harvest` で `docs/question-sets/` に残しておけば、
次回の同種文書はそこから始められる。とくに次の2つは一次資料からは決して得られない。

- 実際に答えてみて**答えにくかった質問**（＝質問の切り方が悪い）
- 書いてみて**必要だと分かった質問**（＝一次資料にも二次資料にも無かった観点）

## 前提

このテンプレートは
[research-project-template](https://github.com/AtsushiHashimoto/research-project-template)
の**上に載せる文書作成レイヤ**である。Issue 階層・worktree・コミット・レビューの
機構はそちらに依存し、ここでは重複させない。

```bash
# 1. 基盤（Issue駆動の機構）
curl -fsSL https://raw.githubusercontent.com/AtsushiHashimoto/research-project-template/main/install.sh | bash

# 2. 文書作成レイヤ
curl -fsSL https://raw.githubusercontent.com/AtsushiHashimoto/document-project-template/main/install.sh | bash
```

### 新規プロジェクトとして始める

```bash
git clone https://github.com/AtsushiHashimoto/document-project-template.git my-proposal
cd my-proposal
./setup.sh "科研費基盤B 2027" "言語駆動ユビキタス環境" "橋本敦史"
```

## ディレクトリ構造

```
my-proposal/
├── .claude/
│   ├── CLAUDE.md                    # プロジェクト固有の設定
│   ├── rules/template/              # テンプレート由来のルール（書き換え禁止）
│   └── skills/                      # doc-* スキル
├── .doc/                            # ★ 必須コンテキスト
│   ├── constraints.md               # 形式制約（項目順・分量・体裁）
│   ├── criteria.md                  # 評価基準と評定要素、読者像
│   ├── graph.md                     # 概念依存グラフ、直列化、対応表、欠落
│   ├── questions.md                 # 質問票と回答（本体）
│   └── sources/                     # 一次資料の保管
└── docs/
    ├── references/                  # 二次資料から採取した知見
    └── question-sets/               # 再利用可能な質問票（次回の資産）
```

`.doc/` は**一次資料とその直接の帰結**だけを置く。
`docs/` は**二次資料と再利用資産**を置く。**両者を混ぜない。**
一次資料が誰かの解釈で汚染されると、次の版で何が変わったか分からなくなる。

## Issue 構成

```
task
 ├─ 1. constraints   形式制約と評価基準の採取・更新
 ├─ 2. graph         概念グラフと質問票の作成・更新
 ├─ 3. draft         執筆（outline → answer を繰り返す）
 ├─ 4. coverage      評価基準への対応の点検と欠落の解消
 └─ 5. polish        推敲・体裁・分量調整
```

文書執筆は「全体を通しで直す」誘惑が強く、直すたびに他所が壊れる。
Issue 単位に切ると、**どの制約を満たすための変更だったか**が後から追える。
共著の場合、記録が無いと善意の第三者が最適化された順序を壊す。
